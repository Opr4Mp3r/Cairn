# Kritt + Cairn：高难度代码审计的组合研究思路

初稿：2026-10-14；更新：2026-10-16。状态：首轮研究思路与实施依据；首轮实现已在独立工作树完成验收，不表示已合并主区。后续上下文整理已在另一独立工作树完成开发自检并停在验收点，未合并或部署。

后续补充：[Cairn 审计上下文最小改造方案](audit-context-minimal-refactor.md)。它具体化各角色读取范围、固定契约注入、节点表达和校验精简，并调整本文第 10.2 节首版导航全量展开 conditions／Open Intents 的交付方式；本文关于条件命题、组合研究及运行边界的约定继续适用；2026-10-16 的运行旁路职责更新以该方案第 1.1 节为准。

## 1. 我们讨论的核心问题

用户希望 Kritt 定期、广泛地审计代码库，积累入口、执行流程、findings 和覆盖信息；Cairn 在固定目标与威胁模型下开展长时间、多 Agent 的深入研究。研究目标通常是成熟项目中难以通过普通审计发现的高影响风险。

这里最重要的能力是**跨分支组合**。假设 A 分支发现一种有条件的能力，B 分支发现另一种能力；两边单独都达不到 Goal，但 A 的输出可能满足 B 的某个输入条件，从而产生新的路径。组合的一端也可能是正常产品功能、JDK 或依赖组件的行为，并非两条现成的漏洞报告。

要解决的问题因此不是简单地把 Kritt finding 批量导入 Cairn，也不是要求每个 Explore 独立找到最终漏洞。我们需要让 Agent 在研究过程中保存可复用的局部知识、发现互补关系、验证连接是否真实，同时始终保留 Goal 的攻击者能力、默认部署和威胁边界。

本次讨论还涉及六个直接影响该目标的现实问题：

1. Reason 经常在单次 240 秒限制下超时，失败后容易从头重试。
2. 旁路 Overseer 与主研究流程的关系曾被理解为“Fact 要等审核才能继续”，与用户期望不符。
3. Fact 与 Intent 粒度过大，整张图对 Agent 的阅读负担增长很快。
4. 长任务容易遗失约束、夸大条件性发现，或者寻找 Goal 的文字漏洞。
5. 固定源码与实验目录混用，正常构建可能污染源码基线。
6. 研究停滞时 Agent 倾向继续查应用 Java 代码，缺乏审视实际 JDK、框架、系统组件及其组合行为的视角。

### 1.1 已对齐的方向

| 事项 | 当前共识 |
| --- | --- |
| Reason 时限 | 将单次调用超时目标值设为 **1800 秒**；现有代码与配置仍需另行修改。 |
| Overseer | 独立旁路观察未结 Intent，按需读取 Fact 线索，仅通过 Hint 纠偏；不逐条批准 Fact，也不阻塞研究或结案。 |
| 终点判断 | 研究期间可以使用待确认观察提出新假设；满足 Goal 的申请仍须独立终审和足够证据。 |
| 研究粒度 | Intent 围绕值得深入研究的假设；Fact 保存可供其他方向复用的结论。难题允许长时间、多轮工具操作。 |
| 研究范围 | 可从应用代码追到实际使用的 JDK、框架、系统组件和部署环境，研究它们与目标项目的关系。 |
| 实验环境 | 用简单、独立的可写副本进行构建和实验，固定源码基线用于版本与证据锚定。 |
| 控制夸大 | 固定目标契约；监督持续纠偏；条件性技术发现与“满足本次 Goal”分别判断。 |
| 组合成立 | 验证同一允许环境中的连续状态变化，解释前一步如何满足后一步条件。 |
| 选材与规划 | 按当前缺口判断材料价值；保留局部搁置理由和重开条件，避免反复规划同一方向。 |

“等待 Overseer 审核后才允许新的探索”是讨论中已撤回的建议，不作为后续设计前提。某个 Fact 尚未获批，不妨碍 Agent 用它安排验证或寻找组合；它的未确认状态必须随之传递。

## 2. 第一性原理：研究系统到底在积累什么

高难度审计是一项有边界的未知状态空间搜索。用户给出目标效果、初始攻击者能力和实际部署。研究者不知道路径，甚至不知道是否存在路径。每轮工作要减少一个具体的不确定性，或获得一个此前未被考虑的能力。

因此，黑板上有三种不同内容：

| 内容 | 含义 | 在 Cairn 中的合适位置 |
| --- | --- | --- |
| 待检验的研究假设 | “条件 P 成立时，A 的结果也许能进入 B” | Intent |
| 可复用的局部结论 | 已观察到什么、成立条件、限制、证据位置与未确认处 | Fact 及关联材料 |
| 一次执行的经过 | 会话无工具、CLI 超时、命令退出、尝试次数 | 运行回执和调度状态 |

有效的局部结论可以描述缺口或阻断。例如“此方向在默认配置下受条件 C 阻挡”，不仅能防止重复研究，也可能使另一个分支产生“能否满足 C”的连接假设。局部排除不能被提升成“整个 Goal 不可能”。

组合研究可以用下面的形式思考：

> 允许的初始状态 S0 → 执行 A → 状态 S1 → 执行 B → 状态 S2。新的 Intent 检查 A 的输出是否满足 B 在 S1 中的输入要求，B 所依赖的其他条件是否仍然成立，以及 S2 是否达到目标效果。

分别证明 A、B 在某些条件下成立，并不能证明存在上述连续过程。例如，A 修改磁盘配置，B 使用启动时缓存；两条结论都正确、配置路径也相同，修改却不一定影响 B。桥接研究要交代传递的具体对象、作用范围、身份、状态变化与生效时序。

Goal 约束攻击者的初始能力。后续能力可以由前序步骤获得，但每次增长必须有来源；不能把尚未获得的权限或管理员准备步骤当作初始条件。前提也不要求全部在 S0 已经成立，应说明哪些由前序步骤满足、哪些属于部署条件、哪些仍然未知。

### 2.1 三个需要分别回答的问题

| 问题 | 判断内容 |
| --- | --- |
| 局部结论真实吗？ | 声明条件下的机制是否得到证据支持。 |
| 能接入当前路径吗？ | 条件如何满足、对象是否对应、状态和顺序是否兼容。 |
| 满足本次 Goal 吗？ | 完整路径是否遵守初始能力、部署、信任边界及目标效果。 |

verified 表示声明的命题得到支持。例如“条件 P 下行为 X 成立”已验证，不代表 P 已在本次部署成立。一个结论可以真实、可供探索引用，但暂不能接入当前路径，或不满足本次 Goal。现有 conditions、premise_ids、review_status 与文字说明承载这些区别；不为三项判断增加状态枚举或通用条件求解器。

这里的“能力”是供 Agent 组织推理的语言，不要求先建立覆盖所有技术场景的枚举本体。程序保持身份、版本、引用及已声明依赖的一致性；LLM 判断条件的语义及潜在连接；Explore 核验连续过程，Overseer 指出遗漏和夸大。字段合法、哈希一致、前提节点均为 verified，不自动证明这些条件能在同一路径中实现。

## 3. Cairn 原有设计能提供什么

Cairn 的原始协议把 Fact 定义为确认的客观事实，把 Intent 定义为从一个或多个 Fact 出发的行动。Intent.from 支持多个来源，图可以表达 A、B 两个分支共同支持一个新探索。Hint 位于事实图外，适合人工或旁路 Agent 注入策略纠偏。

这套结构天然适合组合研究：A、B 可并行探索，各自落下局部知识；Reason 在共享图上识别交点；新的 Explore 验证桥接假设。实际项目中已有多来源 Intent，说明图协议无需推倒重来。

现有审计实现已明确区分：Intent.from 是研究来源和材料线索，Fact.audit.premise_ids 才是结论的逻辑依赖。多来源 Intent 表示“这些材料值得共同研究”，并不证明它们已经能组合。旧实现曾允许 Overseer 更正 Fact 前提并使依赖后代降回 unverified；2026-10-16 的新决定停止这条运行旁路写 Fact 路径，历史状态与记录保留，运行纠偏仅写 Hint。

但**结构上允许组合，不代表 Agent 会稳定地发现组合**。Agent 的注意力会偏向当前 Intent、最近的 Fact 和显眼的高排名 finding。跨分支关系可能使用不同术语；低影响观察或正常组件行为也可能是另一条路线缺失的关键条件。如果材料无法按需找到，或者每轮必须读完整篇长报告，图的表达能力就不能充分变成研究能力。

本次运行还说明审计版 Fact 的语义与原始协议存在张力：研究 Worker 的观察初始标为 unverified，运行 Overseer 只观察 Intent；候选证明由独立终审核验。后续 Worker 可以将其作为待验证线索，提出更深探索；完成申请不能把未经支持的前提当作证明。图和提示词必须始终传递这一层次，不能因为名称叫 Fact 就让 Agent 自行假定全部已经证实。

## 4. Kritt finding 的实际形状与适用性

本次 JeecgBoot 研究固定使用 Kritt scan 1 的已保存视图。快照含 83 条入口、873 条流程、797 条原始 finding，其中 456 条标为 canonical；另有 307 条流程没有 finding。这里的计数只说明该快照的材料规模，不表示对应风险已被 Cairn 独立证实。

一个 finding 的九个内容字段为 explanation、exploitable、file_path、line、malicious_actor、malicious_input_example、summary、trigger_flow、vulnerability_type。表层另有 bounty_rank、影响级别、去重簇与父流程等信息。实际 finding 会在文字中叙述入口、攻击者身份、数据流、限制条件、依赖组件和可能效果，trigger_flow 保留有序站点。

这些内容很适合做研究线索，但其形态更接近**独立漏洞报告**。组合研究最关心的“该材料产生哪项局部能力、需要什么输入、作用于哪个对象、哪里仍被阻断”常散落在 explanation 与 trigger_flow 中。Agent 得先提炼，才能将它与另一分支比对。Kritt 的 rank、canonical、exploitable 和后处理标签只能辅助选材，不能替代这一提炼与代码级复核。

仅看 findings 也不够。正常功能、受限路径和无 finding 的流程，可能为另一条分支提供必要条件，或者证明组合走不通。Kritt 已有入口、流程与执行信息，应继续作为研究材料，而不应仅把“报告为漏洞”的记录交给 Cairn。

材料价值随当前缺口改变。低影响记录可能提供关键条件，高排名 finding 也可能与当前路径无关。Reason 应问“哪条材料能改变对当前缺口的判断”，不直接以 bounty_rank 作为研究优先级。Builder 负责目标解释、可信起点与材料入口；研究期由 Agent 持续调整选材。

### 4.1 当前交接的实测限制

本次 Builder 从固定视图展开交给研究工作区的材料共 57 条，其中 10 条是 finding；完整视图仍保存在本次 run 中。研究角色的明确输入主要指向这批已选材料。Builder 拥有 describe/search/get 命令，但同一查询入口并未作为研究角色明确可用的工作入口交付。这容易把开题时的一次选材变成长期研究的注意力边界。

现有 search 适合定位已知词语，却难以直接查找互补能力。一次 effect=rce 查询在该快照命中 764/797 条 finding，几乎没有筛选力；搜索结果按记录 ID 而非与当前缺口的关系排序。get 会展开父流程、生成记录、同去重簇和后处理历史，它不会自动发现另一个独立分支与当前 finding 的功能互补关系。

因此，现版 Kritt+Cairn **可以偶然完成 A+B 组合，无法稳定保证 Agent 会发现未在开题材料中的 B，或主动复查低排名的互补记录**。

开放全部固定材料只解决访问问题，不能保证 Agent 知道该找什么，也不能补出 Kritt 未曾记录的行为。研究保留两条互补路径：按已知缺口查询入口、流程及 findings；从阻断机制或真实消费者回到固定源码重新推导。检索未命中不能推出能力不存在。

## 5. 合适的 Intent 与 Fact 粒度

“一条 Intent 解决一个问题”不应退化成按函数、文件、接口逐项勾选。用户设定的是成熟项目中的高价值难题，真正有用的 Intent 应给予 Worker 足够的研究空间，例如检验某个可组合的能力、跨层假设或部署条件。它可以涉及多个文件、依赖实现和本地实验，也可以在同一 session 中修正自己的中间假设。

判断是否拆出新 Intent，主要看三件事：是否出现可独立推进的假设；是否有能让另一 Worker 使用的稳定局部结论；是否能在减少重复上下文的情况下并行。两条路线可以共享 Fact；“互不重复”指避免做同一研究工作，不意味着不能引用相同前提。

Fact 的主张应方便其他 Worker 引用。可按以下顺序表达，不要求建立复杂的新字段体系：

1. 在哪些身份、部署、数据、版本条件下观察到什么；
2. 由此得到什么能力，作用于哪个对象；
3. 哪些限制或反证仍存在；
4. 结论处于什么验证层次，详情与原始证据在哪里。

短结论必须保留决定组合的差异。例如“影响某对象”需要保留对象归属和作用范围，“改变配置”需要保留影响磁盘还是当前进程、何时生效。摘要可能完全正确却遗漏连接所需的细节；Agent 应在摘要不足以判断时打开原材料补齐，而不是把缺失条件理解为没有限制。

Fact 粒度以能独立引用、能独立反驳的主张为准。首版让 description 首段给出带关键条件的主要结论，后续段落保留细节；conditions 不因追求简短而删减。旧 Fact 不批量改写。程序可生成带原文入口的机械导航，不能把截断预览称为完整结论。

一次复杂探索可能涉及多个观察。当前协议通常由一个 Explore Intent 收束为一个 Fact，因此应首先改好任务边界和主要结论的写法。若多个观察会分别被其他分支复用，再评估同一探索写入多个 Fact 的协议修改；不要为追求短节点而强迫 Worker 每读一个文件就创建一条 Intent。

执行环境故障没有形成目标项目的新知识时，应记录为执行失败，保留可重试的研究方向。本次出现过“本 session 零执行”的长 Fact，后续又围绕它安排重试，说明该界线需要落实到收尾行为，而非只在文案里说明。

## 6. 让 Agent 持续发现跨分支连接

Reason 应在下列事件发生时考虑组合：新能力或新限制进入图、某条路线被具体条件阻断、已有结果被纠偏、当前候选无法达到 Goal。它需要回答三个开放问题：

- **新能力能做什么？** 是否能满足其他路线此前缺少的输入或权限？
- **当前缺少什么？** 固定 Kritt 材料和已有 Fact 中，是否有其他分支能提供？
- **两端能否接上？** 对象、身份、租户、作用范围、版本、默认配置和时序是否一致？

任务说明还应点明“本轮要查清哪个未知、什么观察会改变判断”。桥接 Intent 重点检验 A 之后的状态能否支持 B；允许明确否定某个连接，不要求每个分支独立完成 Goal。

发现一个有希望的连接时，Reason 创建多来源 Intent，明确待验证的桥接条件。Explore 负责读足材料、实验和寻找反例。结果可以是成立、仅在条件下成立，或者被具体约束阻断。单个分支即使未完成 Goal，其局部能力仍应可被其他路线使用。

这是一种 Agent 的研究行为，而不是对全部 finding 两两枚举后自动宣告漏洞。大量组合只在字面上相似；LLM 的优势在于跨术语、跨模块发现值得验证的假设，它的弱点是会忽略隐藏条件或把相似对象误当同一对象。程序保持证据引用，Agent 对连接负责，旁路监督检查条件偷换。

### 6.1 当应用层调查陷入瓶颈

Reason 还应追问：当前路线依赖了哪个底层安全假设？实际运行版本的 JDK、框架、操作系统或高影响组件是否保证该假设？不同层的处理顺序或语义差异能否与已获得的局部能力结合？

深入调查必须从目标项目真实调用的函数、依赖版本与部署环境出发。发现某个 JDK 或组件的通用行为，只是一个新研究线索；仍需验证它在本项目链路中的可达性、攻击者控制与效果。深入层次可以扩展，Goal 的攻击者起点和部署条件不会因此被放宽。

### 6.2 研究注意力与规划记忆

Reason 优先选择能够改变研究判断的未知条件：一次检查可能同时排除多条候选，也可能连接几个独立观察。判断依据写在任务说明中即可，不引入评分公式、优先级参数或新的调度角色。

除图中知识外，Reason 还应保留简短的规划备注：考虑过哪些连接、为何暂搁、需要什么新证据才能重开、下一步最值得查清什么。备注属于可修订的工作记忆，不作为 Fact、验证证据或新 Goal；当前图、Hint 和固定 policy 始终优先。执行失败则沿用运行回执，向下一次调用提供失败原因和原记录入口，不转为源码反证。

局部暂搁表示不在没有新依据时反复派发同一方向；已有局部结论仍可复用，其他方向继续研究。本轮不增加 dormant、全局“方向耗尽”等状态。没有待执行方向时，Reason 应具体说明改变哪种检索视角或调查哪个缺口，避免仅换措辞重复派发；有在途任务时可沿用现有空动作等待。暂搁不形成“证明不可能”的完成出口，也不自动停止整个项目。若受工具或材料缺失阻塞，沿用现有执行失败／拒绝记录，不伪造研究成果。

这里仅暂搁局部分支，保留现有 Reason 动作契约。当前代码在 Open Intents 为空时拒绝空结果；本轮不单独放宽该校验，也不新增“无方向且成功”的返回值。否则可能造成重复 Reason 或无人唤醒的静默空转。全局无可执行方向的退避／唤醒机制留待实际需要时另议，不能把它隐藏在提示词修改中。

## 7. 如何利用 Kritt 的全部材料，且保持系统简单

优先在 Cairn 的研究期提供与 Builder 同一固定 Kritt view 对应的只读查询入口。Worker 可以在新 Fact 或缺口出现时按需 search/get，得到原始引用、父流程、同簇记录及回执。查询范围固定在任务的 scan 与 commit；Kritt 后续定期扫描产生的新版本，要作为另一次明确选择的材料处理。

首版继续使用现有 search/get，按对象、路径、消费者、所需输入等具体词语检索；搜索过宽时调整问题，不新增语义检索服务。保留所有入口、流程、非 canonical 记录和无 finding 流程的访问能力，按需打开原始材料。

对 Cairn 已有图，程序生成轻量导航：Fact ID、主张预览、完整 conditions、验证状态、premise_ids 和全文入口；Open Intents、Hint 继续可见。导航由已有字段直接渲染，不另调用 LLM，不重写历史主张。语义能力由 Reason/Explore 在实际阅读时提炼。覆盖全部 Kritt finding/flow 的能力索引暂缓，只有现有入口实际不足时再考虑。

如果 Kritt 侧以后增加专门记录局部能力或阻断的输出，应让它们保持“研究观察”的身份。不能为了适配 finding 表而把正常能力或未闭合假设写成确定漏洞。当前 Cairn 适配器要求现有 json_answer 的字段集合与步骤 schema 完全相等；直接新增字段，需要同步更新适配契约。

## 8. Overseer 的位置与 Goal 约束

2026-10-16 更新：本节运行期监督职责以[上下文改造方案第 1.1 节](audit-context-minimal-refactor.md#11-2026-10-16-决定旁路只纠偏-intent)为准，取代原先逐 Fact 复核的实现安排；开题种子复核与独立终审继续保留。

Overseer 独立旁路只观察未结 Intent，按需读取来源 Fact 作线索。它通过具体 Hint 指出方向偏移、条件隐藏、前提跳跃或预设目标成立；正常方向不发 Hint。不逐条复核 Fact、不修改其状态、不取消 Intent，其执行与重试不阻塞研究或结案。

主流程必须区分“探索可以依据它提出问题”和“完成证明可以依赖它”。未经复核的记录可以用于提出问题，也可以作为非 refuted 候选提交独立终审；终审独立核验候选、真实必要前提及条件，不以 verified 标签代替证据。若 Overseer 自身缺文件工具、调用超时或输出无效，这是复核执行问题，不是项目源码的反证，也不应转成研究 Agent 必须重新发现的代码缺口。

目标契约需要每轮可见且简短：目标效果、允许的攻击者初始能力、部署基线、信任边界、必要证据与明确排除的条件。监督重点是实际链条是否引入了新的登录身份、管理员准备步骤、非默认配置或其他用户未授权的前提。

例如，“无需有效登录凭据”是否接受公开默认口令、是否接受先从匿名链获得凭据再登录，属于开题时需要固定的政策解释。研究 Agent 可以报告技术机制和必要条件，不能在找到结果以后选择对自己有利的目标含义。技术上成立而不满足本次 Goal 的结果仍可作为有条件观察保留。

## 9. 运行层调整

**Reason：** 使用已有 tasks.reason.timeout，将新审计任务的单次执行上限设为 1800 秒；不增加第二个超时参数，也不改变心跳租约、项目预算或其他角色时限。现有提交会保存 tasks 执行快照，修改示例 YAML 不会热更新已有项目；本方案不静默迁移当前研究。时限只提供执行空间，不要求每轮运行满 30 分钟。

图按需阅读：先看导航和上轮规划备注，再打开与当前缺口有关的事实、Hint、Kritt 原文与源码。格式错误、超时和工具故障保留各自已有错误信息。下一轮复用最近成功的规划备注和最近失败的简要原因，避免无信息地从头重试；首版不承诺恢复超时前尚未输出的思考，不新增会话续接协议。完整证明和独立终审仍可取得原始依据。

**源码与实验：** 固定源码保持证据与版本基线。需要构建或运行时，提供独立可写副本；构建输出、临时数据和实验日志放在副本或任务工作目录，留明实验与默认部署的差异。优先复用现有本地目录和复制方式，不引入新环境管理平台。本次 Maven target 输出污染基线、导致 Resume 拒绝，说明该隔离值得落实。

**服务与材料：** Kritt 继续定期更新自己的数据库；Cairn 服务仍由用户手动启动。Builder 可与用户交互、选定本次 Kritt scan、提交研究；研究期读本次固定材料，不让每轮扫描结果悄悄替换已有项目的证据基线。

## 10. 最小落地方案与开发顺序

本节用于后续开发分工，本轮仅改文档。沿用当前 audit 流程、harness／资源池、图协议、旁路监督和独立终审；generic 行为保持。首版不改 Kritt 数据库、工作流或输出 schema，不增加 Agent 角色、服务进程、审批步骤或数据库表。

### 10.1 哪些由提示词完成，哪些必须由程序完成

| 改动 | 提示词／Skill 负责 | 确定性代码／配置负责 | 最小落点 |
| --- | --- | --- | --- |
| 顺序组合、条件命题 | Reason 提出桥接假设；Explore 核验 A 后的状态；Overseer／终审区分机制真实、路径兼容、Goal 达成 | 继续使用现有来源、前提、条件和证据规则，不增加条件求解器 | audit Reason／Explore／Conclude 及现有审核提示词 |
| 按缺口取材 | Builder 交付起点与材料入口；Reason／Explore 按对象、输入、阻断条件查询，必要时返回源码独立发现 | 向研究工作区交付固定 view 的查询上下文和可执行命令；复用查询与回执实现 | controller/research.py、audit.py、service.py 的工作区交付；dispatcher/tasks/audit.py |
| 可复用结论与图导航 | Fact 首段保留主要结论及关键限制；Reason 先导航后原文，不把预览当证明 | 从现有图字段生成导航文件，保留全文；不调用额外摘要 Agent | audit_inputs.py、dispatcher/tasks/common.py 及 Reason 输入 |
| 规划记忆 | Reason 简述已考虑连接、缺口、暂搁原因、重开条件；当前图和 policy 优先 | 保存并提供最近成功规划备注，附原回执及图版本；提供最近失败原因 | dispatcher/tasks/reason.py、tasks/audit.py 的输入／输出与回执 |
| 失败与局部暂搁 | 零观察时返回既有拒绝格式；故障不写成 Fact；已查过的分支有新依据才重开 | 复用现有失败／拒绝、释放与重试路径；不增加全局空闲动作或分支状态 | Explore／Conclude 提示词、已有运行回执；Reason 动作契约保留 |
| Reason 时间空间 | 把时间用于解决具体未知，避免每轮重读全部历史 | 在审计示例及新任务配置使用现有 tasks.reason.timeout=1800 | dispatch.service.example.yaml、dispatch.builder.example.yaml、dispatch.audit.example.yaml 及使用说明 |

表中的职责划分不要求把研究判断变成字段。候选排序、语义连接、条件是否满足由 Agent 负责；程序只提供稳定输入、材料访问、已有状态语义和持久化。

### 10.2 三项必要的数据交付

**固定 Kritt 查询入口。** 复用 `python -m cairn.controller.kritt_query --context ...`，由程序提供完整命令与输入示例。研究读取本项目已提交快照的 view，不指向 Builder 可继续编辑的原始选材，也不在运行期重新查询最新数据库。工作区查询上下文沿用该 view 的身份，把 `queries_dir` 指向研究工作区；复用现有每次调用独立保存 request、materials、receipts 的行为。

激活与恢复都补齐入口，包括已经存在 input.json 的工作区。命令按实际安装环境和提交快照位置生成，不照搬 prepare 时可能已过期的命令。并发 Worker 使用各自查询回执，不调用 collect_queries 覆盖开题材料或共享汇总；新增材料仅供后续研究引用，不自动晋升为已验证 Fact。原材料缺失时明确报告，不偷换 scan；源码研究入口仍独立存在。

**图导航。** 在已有 graph.yaml 旁生成 graph-index.md，包含 Fact ID、首段预览、完整 conditions、review_status、premise_ids，以及在原图中定位节点的方式；保留 Open Intents 和 Hint 的入口。长文预览明确标记截断，旧节点不强行生成语义摘要。完整图仍可由 harness 自行读取和搜索；不新增图查询服务、向量库或全量源码清单。当前图中的状态和条件每次重新渲染，不能复用过期审批状态。

**Reason 规划备注。** audit Reason 的 data 中增加一个可选字符串 `planning_notes`，与原有 intents／complete／合法空动作一同返回；缺省时兼容旧输出。Agent 用少量文字引用相关 Fact／Intent，说明考虑过的连接、当前缺口、暂搁原因及重开条件，不要求新的嵌套 schema。

程序提取备注后按原有动作契约处理；仅在本轮任务仍有效且动作成功时保存为最近成功的规划记录，与已有研究回执放在一起，并关联原图 revision／回执路径。没有备注的旧输出不清空上一份；失败或迟到结果不覆盖它。下一轮提供备注和来源路径，允许参考上一 generation 的记录但必须结合当前图重新判断。最近失败的类型、简要原因和回执路径单独提供，不把完整 stdout 或全部历史重新拼入 prompt。备注不落 Fact、不写 Hint、不提升 reason_revision，不触发自己的下一轮 Reason；也不允许仅返回备注来绕过空队列的动作要求。

这三项是完成研究行为所需的输入与记忆，不增加用户填写参数。旧项目不重新建图；能从其已有提交材料恢复的信息按需交付，缺少的材料如实说明。

### 10.3 开发顺序

| 顺序 | 工作内容 | 完成后可直接使用的能力 |
| --- | --- | --- |
| 1. 打通材料与时间配置 | 交付研究期固定 Kritt 查询入口，覆盖首次激活和恢复；在审计示例配置写入 1800 秒 Reason 上限，更新新任务使用说明 | Reason／Explore 能在开题材料之外按需取材；新任务使用明确的执行时限 |
| 2. 补图导航与规划记忆 | 生成机械导航；支持可选 planning_notes 的保存／回读；提供最近失败原因；保持原动作和触发规则 | 新一轮能够接着上一轮判断继续，不必先重新理解完整历史 |
| 3. 一次性对齐研究提示词 | 按第 2、5、6 节精简更新 Reason、Explore、Conclude 和现有审核提示词；同步 Builder Skill 中的选材及交付说明、分发包 | 按缺口提出桥接 Intent，验证连续状态变化，保存条件，暂搁重复方向；各角色使用同一命题语义 |
| 4. 跑通最小示例并收尾 | 在隔离样例中运行一次材料互补的研究，再运行一个对象／时序或部署条件不兼容的对照；同步使用说明 | 确认查询、规划、探索、旁路纠偏与现有终审能协同工作，并保留实际限制 |

各步是开发依赖顺序，不新增“开发到此必须停下审批”的检查点。普通回归覆盖固定 view 不漂移、并发查询回执不覆盖、导航保留条件、规划备注不改图状态及旧输出／generic 兼容即可；不另建评测平台，不增加每轮研究前后的自动验收关卡。样例观察桥接是否被提出、条件是否被保留以及最终判断是否正确，不以 Fact 数量或运行时长代替成果。

步骤 3 的实际提示词应保持短小：行为规则、可用入口、输出要求各自集中，避免把本文整篇塞入 prompt。使用新任务样例验证配置生效；当前运行项目不被本轮文档或示例配置修改。调整旧项目执行快照属于另一次明确操作，不为本方案增加热更新接口。

### 10.4 本轮保留的边界

- 原有独立可写源码副本约定继续适用；需要构建的样例先用普通复制在固定源码之外准备副本。首轮静态研究不以开发副本管理平台为前置条件。
- 一次 Explore 写多个 Fact、全 Kritt 能力索引、语义排序、自动匹配条件、全局无方向的退避／唤醒、失败会话自动续接均暂缓；不为未来扩展提前加参数。
- 本轮不扩展 JDK／外部实验产物的结构化证据类型，也不增加 Overseer 优先级调度、监督角色或共同盲点评估流程。原文允许深入依赖调查，仍需如实说明当前证据能支持的范围。
- 1800 秒上限、检索入口和规划记忆都不保证找到目标；未达 Goal 时仍由现有预算与用户控制决定项目结束，不新增负向完成出口。
